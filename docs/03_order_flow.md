# Жизненный цикл заказа

## 1. Общая информация

Заказ проходит полный цикл от создания до выдачи клинике.

Основной процесс:

Клиника / Администратор создаёт заказ  
→ Заказ получает статус `NEW`  
→ Администратор проверяет заказ  
→ Администратор назначает одного или нескольких техников  
→ Заказ переходит в `IN_PROGRESS`  
→ Техники выполняют свои части работы  
→ Каждый техник фиксирует конкретно выполненные им услуги  
→ Система проверяет выполнение всех необходимых работ  
→ Заказ автоматически переходит в `COMPLETED`  
→ Администратор выдаёт готовую работу  
→ Заказ переходит в `ISSUED`  
→ Заказ сохраняется в истории  
→ Через 18 месяцев после выдачи файлы удаляются

Статус заказа и состояние отдельных материалов являются независимыми сущностями.

Например, если необходимо переснять скан, заказ не переводится в отдельный статус и остаётся `IN_PROGRESS`.

---

# 2. Статусы заказа

В MVP используются следующие статусы:

```text
NEW
IN_PROGRESS
COMPLETED
ISSUED
```

## 2.1. NEW — «Поступило»

Заказ создан, но выполнение работы ещё не началось.

Заказ может находиться в этом статусе, когда:

* клиника только что создала заказ;
* администратор ещё не проверил заказ;
* администратор ещё не назначил техников.

## 2.2. IN_PROGRESS — «В работе»

Заказ передан в работу одному или нескольким техникам.

После перехода в `IN_PROGRESS`:

* назначенные техники получают доступ к заказу;
* заказ появляется в рабочих списках назначенных техников;
* начинается выполнение работ.

Минимальное условие перехода:

* назначен хотя бы один техник.

## 2.3. COMPLETED — «Завершено»

Все необходимые работы по заказу выполнены.

Этот статус устанавливается системой автоматически.

Техник не может самостоятельно установить общий статус заказа `COMPLETED`.

## 2.4. ISSUED — «Выдано»

Готовая работа передана клинике.

Переход:

```text
COMPLETED → ISSUED
```

выполняет администратор.

Система сохраняет:

* дату выдачи;
* время выдачи;
* администратора, выполнившего выдачу.

Дата выдачи используется для расчёта срока хранения файлов.

---

# 3. Создание заказа

Заказ может быть создан двумя способами:

1. Клиникой через собственный аккаунт.
2. Администратором лаборатории.

---

# 4. Создание заказа клиникой

Пользователь клиники создаёт заказ через форму.

## Обязательные данные

* ФИО пациента;
* ФИО врача;
* клиника;
* одна или несколько услуг;
* желаемая дата выполнения;
* комментарий;
* необходимые материалы и файлы.

После отправки заказ получает статус:

```text
NEW
```

Система автоматически создаёт:

* уникальный идентификатор заказа;
* номер заказа;
* дату и время создания;
* связь с клиникой.

---

# 5. Создание заказа администратором

Администратор может создавать заказ самостоятельно.

Это необходимо для:

* одноразовых клиник;
* новых клиник, для которых ещё не создан аккаунт;
* частных работ;
* заказов, поступивших другим способом.

Администратор может выбрать существующую клинику.

Также в системе существует специальная запись:

```text
Частные работы
```

Она используется для заказов частных клиентов, которым не требуется отдельный аккаунт.

Создание заказа администратором не требует наличия пользовательского аккаунта клиники.

После создания заказ получает:

```text
NEW
```

---

# 6. Номер заказа

Каждый заказ должен иметь уникальный человекочитаемый номер.

Пример:

```text
DL-2026-001524
```

Номер заказа используется для идентификации заказа:

* в CRM;
* в списках заказов;
* в актах передачи;
* при общении сотрудников;
* при идентификации физических материалов;
* на упаковке;
* на слепках;
* при необходимости в названиях файлов.

Номер заказа не должен повторяться.

---

# 7. Данные заказа

Заказ содержит:

* уникальный ID;
* номер заказа;
* ФИО пациента;
* ФИО врача;
* клинику;
* одну или несколько услуг;
* желаемую дату выполнения;
* комментарий;
* дату и время создания;
* текущий статус;
* назначенных техников;
* материалы и файлы;
* выполненные работы;
* дату и время выдачи;
* пользователя, создавшего заказ.

---

# 8. Услуги заказа

Один заказ может содержать несколько услуг.

Пример:

```text
Заказ DL-2026-001524

1. Безметалловая коронка из диоксида циркония
2. Временная коронка ПММА
3. Индивидуальный абатмент
```

Каждая услуга хранится как отдельная позиция заказа.

---

# 9. Цена услуги для клиники

Цена услуги зависит от клиники.

Одна и та же услуга может иметь разные цены для разных клиник.

Пример:

```text
Стандартная цена коронки: 30 000 ₸

One Dent: 26 000 ₸
Bas Dent: 28 000 ₸
Jana Dent: 30 000 ₸
```

При создании заказа система определяет актуальную цену услуги для выбранной клиники.

Эта цена должна быть зафиксирована в составе заказа.

Изменение прайса клиники в будущем не должно изменять цену уже созданного заказа.

Например:

```text
01.08.2026
One Dent → Коронка = 26 000 ₸

Заказ создан:
Цена = 26 000 ₸
```

Если 20.08.2026 цена изменена:

```text
One Dent → Коронка = 29 000 ₸
```

старый заказ всё равно должен хранить:

```text
26 000 ₸
```

---

# 10. Минимальный срок выполнения услуги

Каждая услуга имеет параметр:

```text
min_days
```

Он определяет минимальный срок выполнения услуги.

Пример:

```text
Коронка — 5 дней
Бюгельный протез — 7 дней
ПММА — 4 дня
```

При создании заказа система должна проверить выбранную дату выполнения.

Если выбранный срок меньше минимально допустимого, заказ не должен быть создан.

Например:

```text
min_days = 7

Сегодня: 10.08
Минимальная дата: 17.08
```

Дата ранее 17.08 должна быть отклонена системой.

Точное правило расчёта календарных/рабочих дней определяется отдельно.

---

# 11. Назначение техников

Администратор может назначить на один заказ:

* одного техника;
* двух техников;
* трёх техников;
* больше трёх техников при необходимости.

Жёсткого ограничения количества техников в бизнес-логике MVP нет.

Пример:

```text
Заказ DL-2026-001524

Назначены:

Омар
Ерасыл
Ертас
```

Все назначенные техники получают доступ к заказу.

Техник может видеть других техников, назначенных на тот же заказ.

---

# 12. Переход заказа в работу

Администратор проверяет новый заказ.

После назначения необходимых техников администратор переводит заказ:

```text
NEW → IN_PROGRESS
```

После этого:

* заказ появляется у назначенных техников;
* начинается выполнение работ;
* техники могут фиксировать выполненные услуги.

---

# 13. Что видит техник

Техник видит только заказы, в которых он назначен.

В заказе техник видит:

* номер заказа;
* ФИО пациента;
* ФИО врача;
* клинику;
* услуги;
* комментарий;
* материалы;
* файлы;
* других техников, назначенных на этот заказ;
* состояние необходимых работ.

Техник не видит:

* цену услуги;
* общую стоимость заказа;
* цену для клиники;
* собственную расценку;
* расценки других техников;
* заработок по заказу;
* финансовые отчёты.

> ⚠️ **<u>Финансовые данные не должны передаваться технику через backend API.</u>**

---

# 14. Выполнение работы техником

Техник выполняет назначенную ему работу.

Техник обязан явно указать, какие конкретно услуги он выполнил.

Пример:

```text
Заказ DL-2026-001524

Услуги:

☑ Коронка
☐ ПММА
☐ Абатмент
```

После выполнения техник нажимает:

```text
Закрыть работу
```

Система создаёт запись о выполненной работе.

---

# 15. Запись выполненной работы

Для каждой выполненной работы сохраняются:

* ID заказа;
* конкретная услуга;
* ID техника;
* дата и время выполнения;
* комментарий;
* историческая расценка техника;
* статус выполнения.

Пример:

```text
Заказ: DL-2026-001524
Услуга: Коронка
Техник: Омар
Расценка: 12 000 ₸
Дата выполнения: 10.08.2026
```

---

# 16. Индивидуальные расценки техников

Разные техники могут получать разную сумму за одну и ту же услугу.

Например:

```text
Коронка

Омар     — 12 000 ₸
Ерасыл   — 10 000 ₸
Ертас    — 13 000 ₸
```

При выполнении работы актуальная расценка техника должна быть зафиксирована в записи выполненной работы.

Изменение будущей расценки не должно изменять уже выполненную работу.

---

# 17. Несколько техников выполняют одну услугу

Одна услуга заказа может выполняться несколькими техниками.

Например:

```text
Заказ DL-2026-001524

Коронка:

Омар     → выполнил свою часть
Ерасыл   → выполнил свою часть
Ертас    → выполнил свою часть
```

Для каждого техника создаётся отдельная запись выполненной работы.

Пример:

```text
Омар:
12 000 ₸

Ерасыл:
10 000 ₸

Ертас:
13 000 ₸
```

Все записи относятся к одной услуге заказа.

---

# 18. Закрытие работы техника

После нажатия:

```text
Закрыть работу
```

работа техника считается выполненной.

Техник не может самостоятельно изменить закрытую работу.

Если требуется исправление:

* администратор может выполнить необходимое изменение;
* изменение фиксируется в истории.

---

# 19. Определение завершения заказа

Заказ не становится завершённым после завершения работы одного техника.

Система должна определить, выполнены ли все необходимые работы по заказу.

Пример:

```text
Заказ DL-2026-001524

Коронка:
Омар      ✅
Ерасыл    ✅
Ертас     ❌

ПММА:
Омар      ✅
```

Заказ остаётся:

```text
IN_PROGRESS
```

После завершения последней необходимой работы:

```text
Все необходимые работы = выполнены
```

система автоматически переводит заказ:

```text
IN_PROGRESS → COMPLETED
```

---

# 20. Кто определяет необходимые работы

При переходе заказа в работу администратор назначает техников и распределяет работу.

Система должна хранить связи между:

* заказом;
* услугой;
* назначенным техником;
* конкретной работой.

Это позволяет определить, какие работы ещё не завершены.

---

# 21. Изменение заказа после начала работы

После перехода заказа в:

```text
IN_PROGRESS
```

редактирование заказа обычными пользователями запрещено.

Администратор может редактировать заказ при необходимости.

В нормальном рабочем процессе изменение заказа после начала работы не предполагается.

Все изменения после начала работы должны фиксироваться в истории.

---

# 22. Материалы заказа

Материалы заказа являются отдельной частью заказа.

К материалам могут относиться:

* сканы;
* слепки;
* фотографии;
* STL-файлы;
* PDF;
* другие необходимые материалы.

Состояние материала не должно менять общий статус заказа.

Например:

```text
Заказ:
IN_PROGRESS

Скан:
требуется переснять
```

Заказ всё равно остаётся:

```text
IN_PROGRESS
```

---

# 23. Повторный скан

В процессе работы может потребоваться повторно снять скан.

В этом случае новый заказ не создаётся.

Администратор добавляет новый файл к существующему заказу.

Пример:

```text
Заказ DL-2026-001524

Скан №1
Статус: устарел

Скан №2
Статус: актуальный
```

Актуальным считается последний подтверждённый файл соответствующего типа.

Предыдущий файл не удаляется сразу.

Он может сохраняться до окончания общего срока хранения файлов.

История загрузки файлов должна сохраняться.

---

# 24. Замена файла

Если новый файл заменяет предыдущий, система должна сохранять:

* старый файл;
* новый файл;
* дату загрузки;
* пользователя, загрузившего файл;
* тип материала;
* информацию о том, какой файл является актуальным.

Обычный пользователь не должен иметь возможности изменить файл другого заказа.

---

# 25. Повторный слепок

Если в процессе работы требуется новый слепок, новый заказ создавать не нужно.

Новый физический слепок должен быть связан с существующим заказом.

Основным идентификатором является уникальный номер заказа.

Например:

```text
DL-2026-001524
```

Этот номер должен быть указан на физическом слепке.

Дополнительно можно указывать:

```text
ФИО пациента
Клиника
```

Но основным идентификатором должен оставаться номер заказа.

---

# 26. Идентификация физических материалов

Для физического слепка рекомендуется использовать маркировку:

```text
DL-2026-001524
Иванов Иван Иванович
One Dent
```

В будущем может быть добавлен QR-код, содержащий идентификатор заказа.

QR-код не входит в обязательный MVP.

---

# 27. Новый материал не создаёт новый заказ

Если материал переснимается или заменяется, новый заказ не создаётся, если это продолжение того же случая.

Например:

```text
Заказ DL-2026-001524

Первый слепок → непригоден
Второй слепок → принят
```

Оба материала относятся к:

```text
DL-2026-001524
```

---

# 28. Выдача заказа

После выполнения всех необходимых работ заказ получает:

```text
COMPLETED
```

Администратор проверяет готовность заказа и передаёт его клинике.

После физической выдачи администратор переводит заказ:

```text
COMPLETED → ISSUED
```

Система сохраняет:

* дату выдачи;
* время выдачи;
* администратора.

---

# 29. Акт передачи

Администратор может сформировать акт передачи по заказу.

Акт должен содержать необходимые сведения о передаче работы.

Постоянное хранение сгенерированного файла акта не является обязательным.

Акт может быть сформирован повторно из сохранённых данных заказа.

---

# 30. Хранение файлов

Файлы заказа хранятся в течение:

```text
18 месяцев
```

Срок отсчитывается от даты выдачи заказа:

```text
issued_at + 18 месяцев
```

Файлы могут быть автоматически удалены после окончания этого срока.

К удаляемым данным относятся:

* фотографии;
* сканы;
* STL;
* PDF;
* другие загруженные материалы.

---

# 31. Данные после удаления файлов

После удаления файлов основные данные заказа должны сохраняться.

Сохраняются:

* номер заказа;
* ФИО пациента;
* ФИО врача;
* клиника;
* услуги;
* дата создания;
* дата выполнения;
* дата выдачи;
* выполненные работы;
* техники;
* исторические расценки;
* исторические цены;
* необходимые данные для отчётности.

Это необходимо для:

* гарантийных случаев;
* внутренней отчётности;
* расчёта заработка;
* истории взаимоотношений с клиниками.

---

# 32. История заказа

Система должна сохранять историю важных действий.

Примеры:

```text
ORDER_CREATED
ORDER_UPDATED
ORDER_STATUS_CHANGED

TECHNICIAN_ASSIGNED
TECHNICIAN_REMOVED

WORK_COMPLETED
WORK_UPDATED

FILE_UPLOADED
FILE_REPLACED
FILE_MARKED_OUTDATED

ORDER_COMPLETED
ORDER_ISSUED
```

Для каждого действия сохраняются:

* пользователь;
* роль пользователя;
* действие;
* объект;
* дата и время;
* при необходимости старое значение;
* при необходимости новое значение.

История не должна редактироваться обычными пользователями.

---

# 33. Отчётность по техникам

Администратор должен иметь возможность получать отчёт по выполненным работам.

Фильтры:

* техник;
* период;
* услуга;
* клиника;
* заказ.

Например:

```text
Техник: Омар
Период: 01.08.2026 — 31.08.2026
```

Результат:

| Дата  | Заказ          | Клиника  | Услуга  |  Выплата |
| ----- | -------------- | -------- | ------- | -------: |
| 05.08 | DL-2026-001524 | One Dent | Коронка | 12 000 ₸ |
| 07.08 | DL-2026-001530 | Bas Dent | ПММА    |  5 000 ₸ |
| 10.08 | DL-2026-001551 | One Dent | Коронка | 12 000 ₸ |

Итог:

```text
Общая сумма: 29 000 ₸
```

Отчёт должен использовать исторические данные выполненных работ.

Изменение текущей расценки услуги не должно изменять старые записи.

---

# 34. Финансовая информация

Финансовая информация является конфиденциальной.

К ней относятся:

* цена услуги для клиники;
* итоговая стоимость заказа;
* расценка техника;
* заработок техника;
* общая сумма выплат по заказу;
* финансовые отчёты.

Финансовые данные доступны только администраторам.

> ⚠️ **<u>Техники и пользователи клиник не должны получать эти данные через API.</u>**

---

# 35. Изменение цен

Изменение цены услуги должно влиять только на новые заказы.

Например:

```text
Старая цена:
One Dent → Коронка = 26 000 ₸
```

Старый заказ:

```text
DL-2026-001524
Цена = 26 000 ₸
```

После изменения:

```text
One Dent → Коронка = 29 000 ₸
```

новый заказ получает:

```text
29 000 ₸
```

Старый заказ остаётся:

```text
26 000 ₸
```

---

# 36. Изменение расценки техника

Расценка техника также должна фиксироваться в момент выполнения работы.

Например:

```text
До 15.08:
Омар → Коронка = 12 000 ₸
```

Работа выполнена 10.08:

```text
12 000 ₸
```

После изменения:

```text
Омар → Коронка = 14 000 ₸
```

работа от 10.08 всё равно остаётся:

```text
12 000 ₸
```

---

# 37. Удаление заказов

Физическое удаление заказов в MVP не предусматривается.

Заказ должен сохраняться для:

* истории;
* отчётности;
* финансового учёта;
* гарантийных случаев.

При необходимости заказ может быть деактивирован или помечен специальным статусом в будущем.

---

# 38. Основные бизнес-правила

1. Заказ может быть создан клиникой или администратором.

2. Администратор может создавать заказ для клиники без пользовательского аккаунта.

3. Для частных работ используется специальная запись `Частные работы`.

4. Один заказ может содержать несколько услуг.

5. Один заказ может иметь несколько техников.

6. Количество техников не ограничивается жёстко бизнес-логикой.

7. Одна услуга заказа может выполняться несколькими техниками.

8. Каждый техник отдельно фиксирует выполненную им работу.

9. У каждого техника может быть индивидуальная расценка на одну и ту же услугу.

10. Расценка техника фиксируется в момент выполнения работы.

11. Цена услуги для клиники фиксируется при создании заказа.

12. Изменение будущей цены не меняет исторические заказы.

13. Изменение будущей расценки техника не меняет исторические работы.

14. Техник не видит никакую финансовую информацию.

15. Клиника не видит внутреннюю финансовую информацию.

16. Техник имеет доступ только к заказам, на которые он назначен.

17. Клиника имеет доступ только к собственным заказам.

18. Файлы доступны только пользователям с соответствующим доступом к заказу.

19. Пересъёмка скана не создаёт новый заказ.

20. Новый слепок не создаёт новый заказ, если он относится к существующему случаю.

21. Физические материалы должны идентифицироваться номером заказа.

22. Повторный материал не изменяет статус заказа.

23. Заказ остаётся `IN_PROGRESS`, пока выполняются необходимые работы.

24. Техник не может самостоятельно установить общий статус `COMPLETED`.

25. Заказ автоматически становится `COMPLETED`, когда все необходимые работы завершены.

26. Только администратор переводит заказ из `COMPLETED` в `ISSUED`.

27. Дата выдачи является началом 18-месячного периода хранения файлов.

28. После удаления файлов основные данные заказа сохраняются.

29. История выполненных работ сохраняется.

30. История важных действий пользователей сохраняется.

31. Физическое удаление заказов в MVP запрещено.

32. **<u>Все проверки прав доступа выполняются на backend.</u>**

33. > ⚠️ **<u>Скрытие данных только на frontend не считается механизмом безопасности.</u>**
